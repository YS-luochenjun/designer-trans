# 存储与执行效率

## 短视频为何可能留下大量中间文件

最终视频的体积与任务工作目录的体积是两个统计对象。工作目录还包含原片、分离音频、历史修复、候选、检查帧、预览、请求和决策回执。

旧媒体处理使用完整无损 RGB 视频保留每次修复的像素。局部只改少数帧，也可能保存一份完整视频；反复抽帧和检查又会积累图片。大量 Agent 轮次、整段解码或编码、文件校验及等待共同影响耗时，不能全部归为模型推理。

逐帧精度用于保护镜头边界、残字和主体，本身有必要。问题在于以整个视频作为每次局部修改的存储单元，以及用过多独立动作处理能够合并的同一问题。减少文件应优先改变表示和留存方式，不能以放宽真实质量问题代替优化。

## 当前已实现的节省

- 内容与帧身份绑定的图像缓存，未受修改影响的帧可复用。
- 局部无损补片，只保存变化像素及父底片引用。
- 显式视频导出与有界依赖链检查点；检查点减少活动链深度，但不会自动删除历史层。
- 写入前空间预检、阶段计时、重复动作意图和无进展动作上限。
- 仅对符合守卫的终态任务提供无引用帧缓存保留计划。

补片模式仍可能解码整段视频，也仍保留历史证据。因此，它主要减少重复完整编码和新增视频存储，不保证总耗时或历史目录立即大幅下降。

## 尚需完善的部分

1. 对稳定底片和同一问题合并检查及修复范围，再保留关键边界的精确验证。
2. 单独度量实际处理、Agent 操作、外部等待与文件校验，不累加嵌套计时。
3. 形成覆盖当前底片、父补片、接受链、候选、工作包及未决请求的完整依赖图。
4. 在依赖图和留存政策允许后，回收失效的完整历史视频及可再生预览。
5. 明确活动证据、近期检查点、历史元数据的分层留存及空间上限。

以上历史媒体回收不能用删除旧日期文件、清空任务目录或删除旧接受记录替代。当前缓存保留接口不等于已经实现活动任务的通用历史媒体垃圾回收。

## 统计与操作边界

应分别报告任务逻辑字节数、最大单文件、各类中间文件数量、活动依赖体积及磁盘实际剩余空间。逻辑字节数和删除后的实际可用空间增量可能因文件分配及其他进程写入而不同。

保持原片、当前结果、依赖链、未决调用证据、费用与私有配置。源码导出只复制白名单项目文件，既不清理生产目录，也不改变制作状态。安装时还应为依赖、模型权重、临时导出及预览另留空间。
