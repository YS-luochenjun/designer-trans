# 项目架构与执行边界

## 主链路

工作台提交需求或原片后，应用层建立任务与语言版本，冻结资源及模型快照。Worker 按工作流依赖运行节点。Agent 产生结构化决定，执行器验证合同、权限、预算、输入文件及实际结果，再保存媒体、回执和状态。

```text
工作台 / HTTP 接口
        |
应用服务：任务、资源、审批、恢复
        |
持久记录与工作流调度
        |
Worker -> Agent 决策 -> 受约束的工具与媒体执行
        |
阶段检查 -> 完整候选 -> 人工视听验收
```

项目不能依赖聊天会话代替生产 Worker。Agent 推理、工具调用、候选质量与最终用户批准分别记录。

## 模块职责

| 模块 | 责任 |
| --- | --- |
| `domain` | 任务、执行、预算、质量和恢复合同 |
| `application` | 创建任务、授权、诊断、定向返工及生命周期协调 |
| `persistence` | 记录持久化与事务 |
| `workflow`、`scheduler` | 节点依赖与调度 |
| `execution` | Work 编排、证据采样、媒体处理、补片、检查点与收敛 |
| `integrations` | Agent、媒体服务与外部需求系统的适配 |
| `interfaces` | CLI、HTTP 接口与运行状态 |

制作路线位于 `execution/clean_routing.py`。技术恢复位于 `application/route_recovery.py`，只执行当前委托允许的恢复动作。Route 不是修改项目源码的维护 Agent。

## 统一媒体执行

现有任务与新任务共用当前媒体执行入口。历史执行标记在读取时兼容，原资源快照、预算和未知结果保持原含义；升级不能成为重做已完成任务或重复调用外部服务的理由。

当前执行层按来源、帧号、解码方式与有效补片复用帧证据。局部修改保存为 `.vpatch.json` 与对应像素文件，引用原底片。完整播放、下游合成等边界再生成实际视频，并核验时钟、像素与音频。清单和补片必须连同其父依赖保存。

## 收敛与恢复

同一底片、范围、能力和分派方法受无进展动作上限约束。语义相同的工具动作不能通过修改理由文本或增加轮次绕过去重。达到上限时记录未解决结果，通过有限制作路线或返工提案继续处理。

对于传输等技术故障，恢复先核对原操作、请求和结果，区分明确失败与可能已派发的未知结果。若原结果存在，优先核验原结果。新动作仍需检查撤销、暂停取消、预算、媒体 SHA 和未决外部请求。

## 验收与后续

工程检查只覆盖其实际测试范围。补片像素一致不证明去字质量；局部接受不证明全片合格；生成可播放视频也不代表用户已批准。最终交付需要对当前具体文件完整视听验收。

接单策略与定向返工已有后端合同和入口，但自动扩大接单、真实时序修复引擎选型、多设备执行及完整 UI 操作仍须按各自范围验证。此源码分发不将这些工作描述为全面完成。
